# spirit — Kotlin Multiplatform

A Kotlin API for [spirit](../README.md), generated from
[`spirit-client-ffi`](../client-ffi) via [uniffi](https://mozilla.github.io/uniffi-rs/),
plus a small demo app: pick a file, mint a Content Identity for it, share it
by QR code, and receive one on another device.

> **Status: builds and passes its JVM tests on Linux; iOS unbuilt.** The
> library AAR, the debug APK, and the desktop target all compile, and
> `:spirit-client:jvmTest` passes against the real daemon over real iroh
> endpoints. The iOS targets are declared but have never been linked — that
> still needs a macOS host with Xcode. The Rust side it depends on
> (`spirit-client`, `spirit-client-ffi`) is built and tested — see
> [`../client`](../client) and [`../client-ffi`](../client-ffi).

## Layout

| Path | What |
|---|---|
| `spirit-client/` | The KMP library: uniffi-generated bindings (not checked in — generated by `generate-bindings`) plus a small hand-written idiomatic wrapper in `commonMain` |
| `demo-app/` | The demo: shared Compose UI in `commonMain`, platform file-picking and QR scanning in `androidMain`/`jvmMain`/`iosMain` |
| `devenv.nix` | The mobile/cross-compilation toolchain (cargo-ndk, Android NDK, iOS Rust targets, Gradle, a JDK) — isolated from spirit's main `devenv.nix` the same way `kai/android/devenv.nix` isolates Android's toolchain from kai's desktop+wasm shell. Heavy, largely unfree tooling has no business in the default shell. |

## Why uniffi, why generated rather than hand-written

`spirit-client-ffi` (in `../client-ffi`) exports `spirit-client`'s API via
`#[uniffi::export]`. uniffi's Kotlin generator turns that into a full Kotlin
API — verified in this repo by actually running it:

```
cargo build -p spirit-client-ffi --bin uniffi-bindgen --features uniffi/cli
./target/debug/uniffi-bindgen generate \
  --library target/debug/libspirit_client_ffi.so \
  --language kotlin --out-dir /tmp/check
```

produces a real `SpiritClient` Kotlin class with `openEmbedded`, `mintCir`,
`putBlob`, `share`, `addPeer`, `offerPairing`, `join`, and so on — one method
per `spirit-client` method, generated, not hand-maintained, so the Kotlin API
can never drift from the Rust one.

That command uses uniffi's standard **Kotlin (JVM/Android, via JNA)**
target — the one proven above. For a genuine multiplatform build (adding
`iosMain`), swap `uniffi-bindgen.rs`'s entry point to the
[`uniffi_bindgen_kotlin_multiplatform`](https://gitlab.com/trixnity/uniffi-kotlin-multiplatform-bindings)
crate (found on crates.io as `uniffi_bindgen_kotlin_multiplatform = "0.1.0"`),
which generates the same API split across `commonMain`/`androidMain`/
`jvmMain`/`iosMain` source sets instead of one JVM-only file. That crate is
third-party and its exact CLI wasn't exercised in this pass — do that swap
and confirm it still generates cleanly against `uniffi 0.32` before building
the `iosMain` half of `spirit-client` for real.

## Building (once you have the toolchain)

```
cd kotlin
devenv shell               # cargo-ndk, NDK, iOS rust targets, jdk 21 + 25

generate-bindings           # uniffi-bindgen -> spirit-client/src/*Main
jvm-native                  # cargo build -p spirit-client-ffi (host triple) — do this first, no mobile toolchain needed
./gradlew :spirit-client:jvmTest      # fastest correctness check

android-native               # cargo ndk ... -p spirit-client-ffi
./gradlew :demo-app:assembleDebug
./gradlew :demo-app:installDebug     # run on an emulator/device

ios-native                   # cargo build --target aarch64-apple-ios[-sim] -p spirit-client-ffi, lipo into an xcframework
# then add demo-app's iosMain target / framework to an Xcode project
```

See `../client/src/lib.rs`'s module docs and `../../wiki/spec.md` for what
each Rust method actually does; the Kotlin names below just mirror them
1:1 (`mintCir`, `putBlob`, `share`, `addPeer`, `offerPairing`, `join`, `want`, ...).
